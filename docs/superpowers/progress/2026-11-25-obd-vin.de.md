# Protokoll zur lokalen VIN

- Den tatsächlichen Integrationsumfang des Benutzers durch eine nur lesende 0902-Abfrage der ausgewählten CAN-ECU fortgesetzt. Kein Internet-VIN-Dienst, keine abgeleiteten technischen Daten, erfundenen Messungen oder vorbelegten Garageneinträge.
- Strikter Decoder, lokale Quellenbelege, erfasste übergeordnete ID, Vergleich des alten Werts bei persistierter Aktualisierung sowie Vorschau-/Bestätigungsoberfläche. Belege bleiben beim Sicherungsexport/-import und bei gewöhnlichen Fahrzeugänderungen erhalten; VIN-Änderung entfernt alte Belege. VIN bleibt außerhalb von KI/Verkaufsberichten.
- Sechs Tests zeigten RED → GREEN, einschließlich einer anfangs schwachen undefined-equals-undefined-Prüfung des Quellenerhalts, die so verschärft wurde, dass tatsächliche OBD-Belege erforderlich sind, sowie einer Regression für Platzhalter aus lauter Nullen. Der Treibertest nutzt das Beispiel aus der öffentlichen ELM-Dokumentation ausschließlich als kontrollierte Fixture an der Hardwaregrenze.
- Letzte Prüfung an der Funktionsgrenze: insgesamt 134 Tests bestanden, Typprüfung/Lint und Web-/iOS-/Android-JS-/Hermes-Exporte mit Exit-Code 0. Ein unabhängiger Prüfer bestand 20 gezielte Tests und fand kein handlungsrelevantes Problem. Kein physisches VIN-Auslesen, keine Prüfung der Fahrzeugechtheit und kein nativer Modaltest durchgeführt.
- Nachfolgende Veröffentlichungsvorprüfung: Expo Doctor fand eine fehlende direkte expo-font-Peer-Abhängigkeit. SDK-kompatibles offizielles Modul über Expo CLI installiert; keine npm-audit-Befunde. Doctor meldet außerdem Classic/TCP in den Directory-Metadaten als ungetestet auf New Architecture; diese Warnung wird nicht unterdrückt. Die Erzeugung nativer Konfigurationen wird separat in einer temporären Kopie geprüft, ohne native Verzeichnisse im Projekt anzulegen.
